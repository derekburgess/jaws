## Context

The starting capture command formats current UTC time to one-second precision and uses it
as `CAPTURE_ID`. Two runs beginning in one second therefore collapse through `MERGE`, even
when they are different evidence sources. The same field also acts as display timestamp,
packet/profile scope, chronological ordering key, and user-facing session reference.

Capture nodes record only source, start, and final packet count. Interrupted imports are
not distinguishable from unfinished or zero-packet captures, imported PCAP perspective is
inferred from the importer machine, and tool/filter/checksum provenance is absent. Scope
is a repeated `CAPTURE_ID` property convention rather than an identified graph object.
Endpoint profile identity similarly has an index but no complete versioned uniqueness key.

The transition must preserve every legacy query while preventing new collisions. It must
also remain standard-library-only in the domain and avoid inventing perspective for old or
imported evidence.

## Decision

### Capture identity and compatibility

New capture identity is `cap_` followed by the 32 lowercase hexadecimal digits of a
random UUID4. The UUID is generated by `UuidCaptureIdGenerator`, an outer implementation
of the existing `IdGenerator[CaptureId]` port. Tests inject a UUID factory or finite ID
generator; domain and service code never obtain identity from time.

Registration time is a separate UTC value. Its legacy second-resolution rendering remains
in `LEGACY_CAPTURE_ID` for display and compatibility. `CAPTURE_ID` continues to carry the
canonical string through legacy packet/profile joins, CLI arguments, and result envelopes,
so existing readers require no immediate query rewrite. The legacy alias is indexed but is
not unique: two legitimate new captures may share one display second.

Existing captures keep their original `CAPTURE_ID`. Migration version 2 copies it into
`LEGACY_CAPTURE_ID` rather than inventing a new identity and risking broken packet/profile
joins. Thus historical IDs remain recognizable legacy IDs while every newly registered ID
has the UUID format.

### Lifecycle and provenance

`CaptureRecord` is an immutable lifecycle snapshot. It records source kind/name, state,
registration/start/end, packet count, content SHA-256 when available, perspective when
known, capture filter, tool versions, legacy alias, and a non-secret failure code.
`CaptureSpec` is the explicit input to new ingest operations: live capture requires a host
entity, while PCAP perspective is optional and must come from the caller or dataset
manifest. A PCAP spec requires its content digest. The ingest service copies these values
without consulting the importer machine.
Transitions follow the already declared state graph:

- `registered` to `running` for a live interface or `importing` for a PCAP;
- an active state to `complete`, `partial`, `failed`, or `cancelled`;
- terminal states do not transition.

PCAP imports are content-hashed in bounded chunks before registration. Live capture
perspective records the selected host IP. Imported perspective remains null until an
explicit capture-host identity is supplied; the importer machine is not evidence of the
original vantage point. Tool versions are canonical JSON because Neo4j properties cannot
store arbitrary maps.

The legacy capture adapter dual-writes `SOURCE`, `STARTED`, and `PACKETS` alongside the new
fields. It finalizes cancellation and exceptions explicitly. If an error path can flush
some pending packets, state is `partial`; otherwise it is `failed`. A normal zero-packet
capture is still `complete`.

### Observation scope and profile identity

An `OBSERVATION_SCOPE` node has unique `SCOPE_ID`, declared `KIND`, creation time,
perspective, and filters. A single capture's deterministic scope ID is `scope_` plus its
canonical or legacy capture ID, connected by `(:OBSERVATION_SCOPE)-[:INCLUDES]->(:CAPTURE)`.
Pooled, custom, and legacy kinds remain distinguishable in the domain contract; later
reference services must not treat pooled scope as chronological history.

`ProfileIdentity` is the tuple of entity ID, scope ID, representation ID/version, and,
when applicable, model ID/revision. Its canonical SHA-256 `PROFILE_KEY` is the storage
uniqueness value. Numeric profiles omit both model fields; an incomplete model pair is
invalid. Version 2 adds the uniqueness constraint without guessing keys for legacy
profiles whose representation/model provenance is unavailable.

## Alternatives considered

### Keep timestamp identity and add microseconds

Microseconds reduce collision probability but still conflate time with identity, depend on
clock quality, and do not make retries or distributed writers unambiguous.

### Adopt ULID or UUID7

Time-sortable identities are convenient, but Python 3.12 has no standard UUID7 generator
and ULID would add a dependency or custom encoding. Chronology already belongs in explicit
timestamps. UUID4 is standard, opaque, and sufficient for uniqueness.

### Rewrite every historical capture and join to a new UUID

This would produce a uniform format but requires coordinated updates across packets,
profiles, artifacts, CLI references, and external notes. Any missed join would orphan
evidence. Preserving historical identity is safer and honest about legacy provenance.

### Infer imported-PCAP perspective from the importing host

This preserves current display behavior but records a false claim whenever a PCAP came
from another machine or dataset. Unknown is an explicit, valid state until metadata exists.

### Use a composite Neo4j profile uniqueness constraint

Neo4j uniqueness constraints do not protect rows when an optional component is null, and
numeric representations intentionally have no model. One canonical non-null `PROFILE_KEY`
supports both modeled and non-modeled profiles.

## Consequences

### Benefits

- Simultaneous capture starts cannot silently merge.
- Human-readable time and durable identity have separate meanings.
- Interrupted evidence has explicit state and bounded provenance.
- Imported perspective is no longer fabricated.
- Scope and profile uniqueness can move behind repositories without changing identity
  again.

### Costs and limitations

- Historical and new `CAPTURE_ID` values have different shapes during compatibility.
- Hashing a large PCAP adds one bounded sequential read before import.
- Legacy captures cannot recover missing end time, filter, perspective, checksum, or tool
  versions; migration leaves unknown values absent.
- `PROFILE_KEY` is populated only by version-aware profile writers, not guessed for legacy
  profiles.

### Follow-on constraints

- New capture writers must receive `Clock` and `IdGenerator` behavior through injectable
  boundaries.
- CLI/MCP adapters may show `LEGACY_CAPTURE_ID`, but all joins and writes use canonical
  `CaptureId`.
- Repository lookups accept canonical ID and an explicit legacy-alias path; they must not
  assume lexicographic ID order is chronology.
- Historical ordering uses capture timestamps, never UUID or alias string comparison.
- Future import specifications expose perspective as an explicit input.

## Benchmark impact

The frozen Benchmark 0 artifacts and detector outputs remain unchanged. Capture/import
result envelopes gain a UUID-shaped `capture_id` and a `legacy_capture_id`, an intentional
post-baseline interface evolution. Packet/profile values continue to join through the
returned `capture_id`. Ranking features, scores, reasons, and synthetic Recall@3 are not
expected to change; the frozen validators and smoke report remain the parity gate.

## Migration

Database migration version 2 is additive. It adds scope/profile constraints and lifecycle
indexes, copies legacy fields into compatibility properties, materializes one scope per
legacy capture, and stamps session-scoped legacy endpoints with `SCOPE_ID`. It never
changes or deletes legacy `CAPTURE_ID`, `SOURCE`, `STARTED`, `PACKETS`, or endpoint scope
fields.

The migration is conditionally reversible before version-2 writers run: objects and
properties created by the migration carry version markers and can be removed while all
legacy fields remain. After new captures or profiles exist, rollback requires export and
restore because removing the new identity semantics would orphan valid evidence.

## Reversal conditions

Reconsider UUID4 if measured collision, interoperability, or distributed-generation needs
require another opaque format. A replacement must remain independent of wall-clock
identity and preserve compatibility aliases. Reconsider graph scope nodes if repository
query measurements show a simpler explicit representation preserves the same semantics
and traceability. Either reversal requires a new migration and superseding ADR.
